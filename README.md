## Частина 1 — Проєктування схеми графа 

```text
       ┌──────────────────┐
       │       User       │
       │------------------│
       │ userId           │
       │ gender           │
       │ age              │
       │ occupation       │
       └────────┬─────────┘
                │
                │ RATED
                │ rating
                │ timestamp
                ▼
       ┌──────────────────┐
       │      Movie       │
       │------------------│
       │ movieId          │
       │ title            │
       │ year             │
       └────────┬─────────┘
                │
                │ HAS_GENRE
                ▼
       ┌──────────────────┐
       │      Genre       │
       │------------------│
       │ name             │
       └──────────────────┘  
``` 


### Які сутності стали вузлами, а які — ребрами? Чому?

Користувачі, фільми та жанри представлені вузлами, оскільки це самостійні сутності з власними властивостями: 

**User** — користувачі системи
**Movie** — фільми
**Genre** — жанри фільмів

Оцінювання та належність до жанру представлені ребрами, оскільки вони описують взаємозв'язки між цими сутностями:

**RATED** — користувач оцінив фільм
**HAS_GENRE** — фільм належить до певного жанру 


### Оцінка користувача — це ребро RATED чи окремий вузол Rating?

Оцінка користувача представлена ребром:

```cypher
(:User {userId: 1})
-[:RATED {rating: 5, timestamp: 978300760}]->
(:Movie {movieId: 1193})
```

Оцінка й час логічно належать до відношення між користувачем і фільмом.  
Окремий вузол Rating був би корисним, якби потрібно було зберігати історію зміни оцінок, джерело оцінювання, коментарі або інші метадані. 


### Чому жанри краще зберігати як окремі вузли Genre?

Окремі вузли Genre дозволяють:

- Знаходити всі фільми певного жанру
- Аналізувати середні рейтинги жанрів
- Визначати жанрові вподобання користувачів
- Уникати дублювання назв жанрів  



## Частина 3 — Основні запити та аналіз результатів 

### Що означає довжина шляху в даному контексті?

Довжина шляху — це кількість ребер, які потрібно пройти між двома користувачами у графі. Один хоп (hop) означає перехід по одному ребру RATED.


### Що означає шлях довжини 2?

Шлях довжини 2 означає, що два користувачі оцінили один і той самий фільм:

```text
User 1 → Movie ← User 2
``` 
Тобто між користувачами є один спільний фільм.


### Як інтерпретувати шлях довжини 4 та 6?

Довжина 4: користувачі пов'язані через два фільми та одного проміжного користувача:
```text
User 1 → Movie 1 ← User 2 → Movie 2 ← User 3
```
Довжина 6: користувачі пов'язані через три фільми та двох проміжних користувачів:
```
text
User 1 → Movie 1 ← User 2 → Movie 2 ← User 3 → Movie 3 ← User 4
```
 

## Частина 4 — Виявлення супервузлів (Supernodes) 

### Які вузли виявилися супервузлами? Скільки у них зв'язків? 

За результатами аналізу було визначено такі супервузли:

**Серед користувачів:** User 4169 — 2314 зв'язків.
**Серед фільмів:** American Beauty (1999) — 3428 зв'язків.
**Серед жанрів:** Drama — 1603 зв'язки, Comedy — 1200 зв'язків.

Ці вузли можна вважати супервузлами, оскільки вони мають значну кількість зв'язків порівняно з іншими вузлами відповідних типів. 
Особливу увагу варто приділити жанрам Drama та Comedy, оскільки вони пов'язані з великою кількістю фільмів.


### Чому запити до супервузлів працюють повільніше?

Запити до супервузлів можуть вимагати обходу тисяч суміжних ребер. Це збільшує кількість операцій, використання пам'яті та час виконання. 


### Яку стратегію оптимізації можна застосувати? 

Особливу увагу варто приділити жанрам Drama та Comedy, оскільки вони мають найбільшу кількість зв'язків із фільмами. Для них доцільно попередньо обчислювати статистику та уникати непотрібних обходів усіх суміжних вузлів. 
Наприклад, можна попередньо підрахувати кількість фільмів кожного жанру та зберегти результат у властивості moviesCount вузла Genre.  


 
## Частина 5 — Graph Data Science (GDS)

### 5.1. PageRank на графі фільмів  

### Що означає високий PageRank для фільму в цьому графі? Це просто «популярний фільм» чи щось інше?

Високий PageRank означає, що фільм займає важливе місце в мережі фільмів, пов'язаних через спільні високі оцінки користувачів. 
Це не просто показник популярності, оскільки алгоритм враховує не лише кількість зв'язків фільму, а й важливість інших фільмів, з якими він пов'язаний. 
Наприклад, American Beauty (1999) має найвищий PageRank — 9.6588. Це свідчить про його центральне положення в мережі та тісний зв'язок з іншими важливими фільмами. 

 
### 5.2. Виявлення спільнот за допомогою Louvain
 
### Чи відповідають отримані кластери інтуїтивним групам?

Так, частково. Наприклад:

Для кожної спільноти було підраховано кількість максимальних оцінок (rating = 5) для фільмів різних жанрів. Після цього визначено три жанри з найбільшою кількістю таких оцінок.  
Порівняння результатів дозволило оцінити відмінності між спільнотами та визначити їхні характерні вподобання. 
Отже, Louvain дозволяє знаходити групи користувачів зі схожими смаками, а аналіз жанрів допомагає інтерпретувати отримані кластери.


### 5.3 Найкоротший шлях між користувачами (Dijkstra) 

### Наскільки «тісний світ» у цьому датасеті?

Для дослідження зв'язності графа користувачів було використано алгоритм Дейкстри (Dijkstra). 
Було перевірено сім пар користувачів. Алгоритм знайшов найкоротші шляхи для двох пар.

Результати:  

Користувач 1	Користувач 2	Шлях	      Вартість	  Довжина
4277	        4169	        [4277, 4169]  0.0048	  1
1680	        3032	        [1680, 3032]  0.012	      1  
Для решти п'яти пар шлях не було знайдено.

Для двох пар, між якими було знайдено шлях, граф виявився досить тісним. Обидві пари мають безпосередній зв'язок через одне ребро SIMILAR, тобто між користувачами немає проміжних вузлів. 
Для решти п'яти пар шлях не знайдено. Це може означати, що користувачі належать до різних зв'язних компонент графа або не мають доступного шляху в побудованій проєкції. 


### Яка середня довжина шляху? Чи підтверджується гіпотеза «шести рукостискань»?

Середня довжина знайдених шляхів:

```text
(1 + 1) / 2 = 1
```

Отже, середня довжина шляху для двох успішно знайдених пар дорівнює одному ребру.

Це менше за шість рукостискань, проте результати не дозволяють підтвердити цю гіпотезу для всього датасету. Для повноцінної перевірки потрібно дослідити більше випадково вибраних пар користувачів, зокрема тих, між якими існують багаторівневі шляхи. 



## Частина 6 — Аналіз і висновки

### 6.1. Граф vs SQL. Які із запитів частини 3 було б складно або неможливо написати в SQL? Чому?

Neo4j та SQL використовують різні підходи до зберігання даних. У SQL інформація зберігається в таблицях, а зв'язки реалізуються через ключі. У Neo4j дані представлені вузлами, ребрами та властивостями. 

Найбільша перевага Neo4j помітна у таких задачах:

- Пошук користувачів зі схожими вподобаннями
- Формування рекомендацій на основі спільних оцінок
- Пошук найкоротших шляхів між користувачами

Наприклад, пошук спільних високо оцінених фільмів користувачів 1 і 2 у Cypher: 

```cypher
MATCH (u1:User {userId: 1})-[r1:RATED]->(m:Movie)<-[r2:RATED]-(u2:User {userId: 2})
WHERE r1.rating >= 4 AND r2.rating >= 4
RETURN m.title, r1.rating, r2.rating;
```

Аналогічний SQL-запит:

```sql
SELECT
    m.title,
    r1.rating AS rating_user1,
    r2.rating AS rating_user2
FROM Ratings r1
JOIN Ratings r2
    ON r1.movie_id = r2.movie_id
JOIN Movies m
    ON m.movie_id = r1.movie_id
WHERE r1.user_id = 1
  AND r2.user_id = 2
  AND r1.rating >= 4
  AND r2.rating >= 4;
```

У SQL пошук шляхів між користувачами потребував би рекурсивних запитів (WITH RECURSIVE) або додаткової логіки для обходу зв'язків між таблицями. Наприклад, для пошуку користувачів, пов'язаних через декілька спільних фільмів, довелося б послідовно виконувати JOIN або рекурсивно обходити зв'язки. 


### Де граф програє? Для яких задач із цим датасетом реляційна модель підійшла б краще?

Попри переваги Neo4j для пошуку взаємозв'язків, графова модель не завжди є найкращим рішенням.

Для датасету MovieLens 1M реляційна модель SQL була б зручнішою для масової обробки даних, формування звітів та виконання агрегатних запитів.

Наприклад, SQL краще підходить для:
- Підрахунку середнього рейтингу всіх фільмів
- Групування користувачів за віком, статтю та професією
- Підрахунку кількості оцінок за роками або жанрами
- Масового експорту користувачів, фільмів та оцінок
- Формування статистичних звітів 


### 6.3. Покращення схеми. Які зміни в схемі прискорили б конкретні запити з частини 3?

Для підвищення продуктивності бази даних можна застосувати такі оптимізації.

1. Оптимізація жанрових супервузлів

Жанри Drama та Comedy мають найбільшу кількість зв'язків із фільмами.

Для них можна попередньо обчислювати кількість фільмів і середній рейтинг:

```cypher
MATCH (g:Genre)<-[:HAS_GENRE]-(m:Movie)
OPTIONAL MATCH (m)<-[r:RATED]-(:User)
WITH g, count(DISTINCT m) AS moviesCount,
     avg(r.rating) AS averageRating
SET g.moviesCount = moviesCount,
    g.averageRating = averageRating;
```

Це дозволяє швидше отримувати статистику жанрів без повторного виконання складних обходів.

 
2. Попереднє обчислення статистики фільмів

Для зменшення повторних обчислень можна зберігати середній рейтинг і кількість оцінок у вузлах Movie.

```cypher
MATCH (m:Movie)<-[r:RATED]-(:User)
WITH m, avg(r.rating) AS avgRating, count(r) AS totalRatings
SET m.averageRating = avgRating,
    m.ratingsCount = totalRatings;
```  

Після цього статистику можна отримувати без повторного обходу всіх зв'язків:

```cypher
MATCH (m:Movie)
WHERE m.averageRating > 4.0
RETURN m.title, m.averageRating
ORDER BY m.averageRating DESC;  
```


3. Обмеження зайвих переходів

Під час пошуку схожих користувачів доцільно використовувати фільтрацію за рейтингом, обмежувати кількість результатів та відкидати користувачів із недостатньою кількістю спільних оцінок.
